## 📝 DESCRIPTION

Diginsight Telemetry `3.8.0` was published to NuGet.org, but corporate policy routes all package
traffic through `https://packagefeedproxy.microsoft.io`. The proxy had not yet synchronised the new
version, so SmartCache — which had been repinned to consume it — could not restore, build, or
publish. The dependency chain was blocked on an event nobody controls.

### Error Message

```
error NU1102: Unable to find package Diginsight.Core with version (>= 3.8.0)
  - Found 135 version(s) in azure-default [ Nearest version: 3.8.0-alpha.5 ]
error NU1102: Unable to find package Diginsight.Diagnostics with version (>= 3.8.0)
error NU1102: Unable to find package Diginsight.AspNetCore with version (>= 3.8.0)
```

### Impact

- SmartCache could not restore, build, or publish against the new Telemetry version.
- The block applied to **all six** SmartCache packages and every dependent repository.
- Retrying was the only available remedy, and it polls an eventually consistent system — there was
  no deterministic completion time.
- Maintainer throughput was gated by consumer-facing distribution latency, which is the wrong
  coupling: feed latency should only affect *consumers*, never the internal release chain.

## 🔬 ANALYSIS

### Root Cause

**A NuGet push and package availability are separate events.** The release pipeline treated them as
one:

```text
Telemetry tag
  → build .nupkg
  → push accepted by NuGet.org        ← pipeline considered itself "done" here
  → NuGet.org validation and indexing
  → corporate proxy synchronisation
  → SmartCache restore can finally resolve   ← but the downstream build actually needed this
```

The downstream build started near the beginning of that timeline while depending on its final step.
Every intermediate stage is eventually consistent and outside the organisation's control.

### Why Retrying Was Not a Solution

Retrying polls a distribution path with no bounded completion time. It cannot produce a deterministic
release process, and it makes release duration a function of third-party infrastructure.

### Why a GitHub Actions Artifact Was Insufficient

Artifacts expire, are scoped to a workflow run, and are awkward to consume. A GitHub **Release**
asset is addressed by an immutable tag, is durable, and can be downloaded directly — making it a
suitable canonical copy of the exact bytes sent to NuGet.org.

### Alternatives Considered

| Alternative | Decision | Reason |
|-------------|----------|--------|
| Retry the proxy until propagation | Rejected | Slow and nondeterministic; retains the root dependency on publication latency |
| Temporarily add direct NuGet.org | Rejected | Corporate access is blocked and it conflicts with source policy |
| GitHub Actions artifact only | Rejected as canonical channel | Artifacts expire and are workflow-run-oriented |
| GitHub Packages NuGet feed | Possible future option | Native NuGet source, but adds authentication and source-mapping complexity plus another feed |
| Build Telemetry from source via project references | Useful for development only | Existing direct-import support helps local coding, but does not validate the exact released `.nupkg` artifacts |
| Copy packages manually between repositories | Rejected | Error-prone, unaudited, and not reproducible |
| GitHub Release `.nupkg` assets | **Selected** | Immediate, versioned, hashable, durable, and usable directly as a local folder source |

SmartCache already supported direct Telemetry project references through `DiginsightCoreDirectImport`
and `DiginsightCoreSolutionDirectory`. That remains useful when developing both repositories together,
but release validation must consume the packaged artifacts to catch packaging, dependency, signing,
and content problems.

### Impact Assessment

| Category | Impact | Severity |
|----------|--------|----------|
| **Release operations** | Dependency chain fully blocked | High |
| **Runtime behaviour** | None — no shipped code affected | None |
| **Reproducibility** | Lock files left half-written by the failed restore | Medium |
| **Developer experience** | Local builds failed identically to CI | Medium |

### Affected Workflows

1. ❌ **SmartCache restore/build** — `NU1102` on all Diginsight package references.
2. ❌ **SmartCache tag release** — cannot build, therefore cannot publish.
3. ❌ **Any other dependent repository** — same failure mode.
4. ✅ **Consumer applications on older versions** — unaffected.

## ✅ SOLUTION IMPLEMENTED

### Fix Overview

Split distribution into two independent channels fed by **one** build:

```text
                            ┌→ GitHub Release assets   (immediate, maintainer-to-maintainer)
tag → build/pack once ──────┤
                            └→ NuGet.org               (eventual, consumer-facing)
```

The GitHub Release is published **and remotely verified** before the NuGet push is allowed to start.
Downstream repositories consume the release assets directly, so their builds no longer depend on
NuGet.org or proxy propagation.

### 1. Producer pipeline (both repositories)

**Location:** `.github/workflows/v3.yml`, `eng/Publish-Packages.ps1`, `eng/package-manifest.json`

A tag push builds and packs once, then:

| Stage | Guarantee |
|-------|-----------|
| Stage and validate | Package IDs, embedded `.nuspec` versions, and symbol packages checked against a tracked inventory |
| Generate metadata | `SHA256SUMS` and `release-manifest.json` produced from the staged bytes |
| Publish release | Assets uploaded, then **re-downloaded and hash-compared** against the staged set |
| Publish NuGet | Separate job, `needs:` the first, gated on `release-verified == 'true'` |

The ordering is enforced structurally, not by convention:

```yaml
permissions: {}                 # top level denies everything

jobs:
  build-and-release:
    permissions:
      contents: write           # only this job may create the release
  publish-nuget:
    needs: build-and-release
    if: needs.build-and-release.outputs.release-verified == 'true'
    permissions:
      contents: read            # cannot touch the release
```

The NuGet credential is scoped to the second job, which has no ability to create or modify a release.

### 2. Consumer bootstrap (SmartCache)

**Location:** `eng/Download-PackageRelease.ps1`, `NuGet.Config`, `artifacts/packages/.gitkeep`

```powershell
./eng/Download-PackageRelease.ps1 https://github.com/diginsight/telemetry
dotnet restore src/Diginsight.SmartCache.slnx --force-evaluate
```

The script resolves the release matching the pinned `DiginsightCoreVersion`, verifies every asset
against the release manifest and `SHA256SUMS`, inspects embedded `.nuspec` identity, and publishes the
`.nupkg` files into `artifacts/packages`. That folder is a declared package source:

```xml
<packageSources>
  <clear />
  <!-- Populated by eng/Download-PackageRelease.ps1. Must exist even when empty, or restore fails with NU1301. -->
  <add key="local-release" value="artifacts/packages" />
  <add key="azure-default" value="https://packagefeedproxy.microsoft.io/nuget/v3/index.json" protocolVersion="3" />
</packageSources>
```

Because the source is declared in the committed configuration, a **plain** `dotnet restore` — and any
Visual Studio or VS Code build — resolves `Diginsight.*` locally while everything else continues to
come from the corporate proxy. No wrapper script, no `--source` arguments, no IDE configuration.

### Solution Features

#### ✅ Build-once integrity
The same staged bytes are uploaded to the release and pushed to NuGet.org. Nothing is repacked
between channels.

#### ✅ Fail-closed verification
Missing, tampered, undeclared, or wrong-version assets abort before anything reaches the local source.

#### ✅ Safe reruns
An existing release is inspected first: matching assets are kept, missing ones uploaded, and any
same-name byte mismatch fails the run. NuGet pushes use `--skip-duplicate`.

#### ✅ Version normalisation handled correctly
NuGet drops a **zero** fourth component only. Both spellings are resolved:

| Source tag | Package version | Filename |
|------------|-----------------|----------|
| `v3.8.0.0` | `3.8.0` | `Diginsight.Core.3.8.0.nupkg` |
| `v3.8.0.1` | `3.8.0.1` | `Diginsight.Core.3.8.0.1.nupkg` |

## 📚 ADDITIONAL INFORMATION

### Measured NuGet Behaviour

Every design decision below was verified experimentally rather than assumed.

| # | Question | Result |
|---|----------|--------|
| 1 | Populated local folder + proxy, no source mapping | `Diginsight.*` ← folder, `Newtonsoft.Json` ← proxy ✅ |
| 2 | **Empty** local folder + proxy | Restore succeeds; everything from proxy ✅ |
| 3 | **Missing** local folder + proxy | `error NU1301` — restore fails ❌ |
| 4 | Suppress NU1301 via `NoWarn` / `RestoreNoWarn` / `WarningsNotAsErrors` | All four attempts still exit 1 ❌ |
| 5 | Relative source path in repo-root config, project nested two levels down | Resolves correctly ✅ |
| 6 | Package already in the global cache | Restore short-circuits in ~8 ms and **never consults sources** |
| 7 | Nearer `src/NuGet.config` vs repo-root config | Nearer file wins; its `<clear />` and mapping apply |

Findings 3 and 4 together are why `artifacts/packages/.gitkeep` is committed: the folder must exist,
and there is no configuration escape hatch. Finding 6 is why any correctness check of source
resolution must run against a clean, isolated package cache.

### Testing

| Suite | Coverage | Result |

| `eng/tests/Publish-Packages.Tests.ps1` | Version normalisation, staging, missing/unexpected package, checksum mismatch | 6 passed |
| `eng/tests/Download-PackageRelease.Tests.ps1` | URL parsing, tag candidates, tampered bytes, wrong repository, version mismatch, missing/undeclared package, `.gitkeep` preservation | 10 passed |

### Migration Considerations

#### ⚠️ `artifacts/packages/.gitkeep` is load-bearing
Deleting it breaks **every** restore in the repository with `NU1301`, including for people who never
use this tooling. It is annotated in both the file itself and `NuGet.Config`.

This is distinct from a fresh clone failing with `NU1102` during a propagation window. Verified on a
fresh clone of `610f828`: the folder is present and empty, the source is valid, and the restore fails
only because the pinned `3.8.0.1` has not reached the proxy — which the download step resolves.

| Situation | Folder | Plain `dotnet restore` |
|-----------|--------|------------------------|
| Pinned version already on the proxy | present, empty | Works |
| Pinned version not yet propagated | present, empty | `NU1102` — run the download step |
| Marker deleted | missing | `NU1301`, always, for everyone |

#### ⚠️ Two `.gitignore` traps
A blanket `artifacts/` exclusion makes re-inclusion impossible — git cannot re-include a path whose
parent directory is excluded. Additionally the Visual Studio template's `**/[Pp]ackages/*` rule
matches `artifacts/packages/`, so the negation must come **after** it.

#### ⚠️ `NU1403` after building an upstream version locally
If the same version was previously restored from different bytes, the global cache disagrees with the
lock file. Purge just that version:

```powershell
Remove-Item "$env:USERPROFILE\.nuget\packages\diginsight.*\<version>" -Recurse -Force
dotnet restore src/Diginsight.SmartCache.slnx --force-evaluate
```

### Security Considerations

- ✅ **Least privilege** — top-level `permissions: {}`; `contents: write` only in the release job.
- ✅ **Credential isolation** — the NuGet credential exists only in the publish job.
- ✅ **Integrity verification** — SHA-256 plus embedded `.nuspec` identity checked before use.
- ✅ **No policy bypass** — third-party packages still come exclusively from the corporate proxy;
  GitHub is used only for first-party assets from the organisation's own repository.
- ⚠️ **Shared trust root** — release assets and their checksums share the same permissions, so the
  hashes protect against corruption and partial upload, not against a compromised release. Repository
  access control, immutable tags, and package signing remain the trust controls.

## 🎓 LESSONS LEARNED

### What Went Wrong

1. **Publication was conflated with availability.** The pipeline treated "NuGet accepted the push" as
   the end of the release, when downstream consumers actually needed the far end of an eventually
   consistent distribution chain.
2. **A failed restore left inconsistent lock files.** Six `packages.lock.json` files were rewritten
   with an incomplete graph and had to be reset before a clean regeneration.
3. **The first design broke IDE builds.** Routing local packages through an ephemeral config passed
   via `--configfile` worked in scripts but was invisible to Visual Studio — meaning a developer who
   simply pressed *Build* still failed. The requirement was developer ergonomics, not just CI
   determinism.

### What Went Right

1. **Measuring instead of assuming.** Seven NuGet behaviours were tested directly. Two contradicted
   reasonable expectations: `NU1301` is unsuppressible, and a warm global cache bypasses source
   resolution entirely. Both would have produced subtly broken designs.
2. **A failing build caught a real defect.** `NU1403` revealed that the committed lock files carried
   hashes from a *local* Telemetry build rather than the published release — which would have failed
   CI's `--locked-mode` restore.
3. **Iterating on the interface.** The design moved from `Restore-WithUpstream.ps1 -Mode Update`
   through a generated overlay to a committed source plus one download script. Each round removed
   concepts; the final form is two commands and no wrapper.
4. **Structural enforcement over convention.** Job dependencies and per-job permissions make it
   impossible for the publish job to run before verification, or to alter a release.

### Improvements for Future

1. **Verify tooling assumptions experimentally before designing around them** — especially error
   suppression, caching, and configuration precedence.
2. **Treat the IDE as a first-class consumer** of any build-configuration change; if it only works
   from a script, it is not finished.
3. **Do not encode a value in two places.** An early draft duplicated the version in
   `upstream-releases.json` and `Directory.Build.props`, requiring a drift check. Reading the single
   MSBuild property removed the file, the check, and the failure mode.
4. **Prefer deleting concepts to documenting them.** The clearest version of this system is the one
   with the fewest moving parts, not the one with the best-explained wrapper.

## 📎 APPENDIX

### A. Diagnostic commands used

```powershell
# Which versions does the proxy actually expose?
$index = (Invoke-RestMethod 'https://packagefeedproxy.microsoft.io/nuget/v3/index.json').resources
$base  = ($index | Where-Object { $_.'@type' -like 'PackageBaseAddress*' })[0].'@id'
(Invoke-RestMethod ($base + 'diginsight.core/index.json')).versions

# Prove the failure is upstream, not a local cache
dotnet restore .\src\Diginsight.SmartCache.slnx --no-http-cache --force-evaluate

# Which source did a package actually come from?
Get-Content "$env:NUGET_PACKAGES\diginsight.core\3.8.0.1\.nupkg.metadata" | ConvertFrom-Json
```

### B. Implementation defects found and fixed

| Defect | Symptom | Fix |
|--------|---------|-----|
| Dot-sourcing a script with its own `param()` block | Caller's `-FromDirectory`, `-Name`, `-Force` silently reset to defaults; script attempted a network download instead of using the local directory | Capture arguments before dot-sourcing; add a dot-source guard |
| Provenance check scanned all cached versions | Any unrelated cached `Diginsight.*` version would fail the build | Scope the check to the pinned version |
| Cleanup failed on read-only and locked files | `Access to the path … is denied` | Clear read-only attributes, shut down build servers, treat the inert cache as best-effort |
| Reuse check validated a feed against its own manifest | A locally staged feed was self-consistent and silently reused instead of the real release | Superseded — the final design always replaces folder contents on download |

### C. Version and tag conventions

- Source tags are four-part: `v3.8.0.0`, `v3.8.0.1`, `v3.7.1.13`.
- NuGet normalises away a **zero** fourth component only, so `v3.8.0.0` → `3.8.0` while
  `v3.8.0.1` → `3.8.0.1`.
- Consequently the tag is **not** simply `"v" + version`; tooling resolves both candidate spellings
  and reports the available releases when neither matches.
